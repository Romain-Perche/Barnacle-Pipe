# Development process (Spec Kit and factory)

The CRM is built in steps, one Linear issue per feature (e.g. `SF-80`, the app skeleton), by an AI
"software factory" with people approving key decisions. Branches are named after the issue
(`sf-80-app-skeleton`).

## Spec-driven development

The repo uses GitHub Spec Kit (`.specify/`). Its workflow
`.specify/workflows/speckit/workflow.yml` runs **specify → review → plan → review → tasks → implement**.
Each feature gets a folder under `specs/<branch-name>/` with:

| File | Contents |
|---|---|
| `spec.md` | User stories, functional requirements (`FR-0xx`), clarifications. |
| `plan.md`, `research.md` | Technical plan and the reasoning behind choices (cited from code comments as `research.md §n`). |
| `data-model.md`, `contracts/` | Tables, routes, settings and commands the feature promises. |
| `tasks.md` | The ordered build tasks. |
| `checklists/`, `quickstart.md`, `design-options.html`, `dependencies.json` | Quality checklist, manual walk-through, UI design options shown to people, dependency choices. |

Code and tests cite these ids (`// covers FR-003, US1 scenario 2`), so a requirement can be traced to
its tests. `.specify/memory/constitution.md` is still the unfilled Spec Kit template.

## Agent skills

`.claude/skills/` holds the skills the factory's agents use: the `speckit-*` commands (specify,
clarify, plan, tasks, analyze, implement, checklist, converge, git helpers), `plan-review` (shows a
person the plan and its open decisions), `plan-fix` (plans a fix after a failed review), `test-recipe`
(maintains `.factory/test-env.md` and `.factory/run/`, see [Testing](../testing/testing.md)),
`visual-briefing`, `ponytail` and `openwiki`.

## Where knowledge lives

- `docs/PRODUCT.md` — product rules; `docs/DESIGN.md` — the visual identity; `docs/DECISIONS.md` — one
  line per choice people made, tagged with the issue key (newest last).
- `README.md` — how to set up, run and configure; `AGENTS.md` — working rules for agents.
- This wiki (`openwiki/`) — how the code works, regenerated by the factory's *Update docs* step.
- [`dataflow/DATAFLOW.md`](../../dataflow/DATAFLOW.md) — data flow diagrams, drawn from
  `dataflow/model.json`, which the same step maintains.
- [`sbom/SBOM.md`](../../sbom/SBOM.md) — every dependency and its exact version, generated from the
  lockfiles; never edited by hand.

## Pipeline

For each issue: specify and plan (with human review), build with tests, AI review and security review
(with fix rounds planned through `plan-fix`), then update docs (data flow model, wiki, SBOM) before the
pull request is merged.
