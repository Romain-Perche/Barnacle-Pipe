# Decisions

The choices people made for this repo, one line each, newest last: `- <the choice> (<issue key>)`.
Product rules are in `docs/PRODUCT.md`, the look and feel in `docs/DESIGN.md`.
Only choices people made: how the code works is in the wiki (`openwiki/`), how to run it in the README.
- The CRM is built in steps, one Linear issue per feature, not in one task (kickoff)
- TypeScript, with Postgres as the database (kickoff)
- The app is hosted on Vercel, and its database is Postgres on Supabase (kickoff)
- Local runs and tests use a local Postgres: developing and testing needs no Vercel or Supabase account (kickoff)
- The production database has a daily backup (kickoff)
- No staging site before the first go-live; tests, local runs and Vercel preview deployments use generated fake data, never the production database (kickoff)
- Sign-in is Google only, through an Internal OAuth app in the barnacle.ai Google Workspace: only barnacle.ai accounts can sign in (kickoff)
- The OAuth client secret and every other secret stay out of the repo and out of issues; tests use a fake Google login (kickoff)
- The first admin is Alexis; an admin can make another user an admin (kickoff)
- Ambassadors are contacts, not users: they never sign in (kickoff)
- A private contact or deal hides it, its emails and its notes from everyone but its creator and its owner, admins included (kickoff; the owner since SF-92 and SF-93)
- Money is in GBP only (kickoff)
- A deal has one main contact plus any number of other linked people; teammates can follow a deal to get its updates (kickoff)
- Anyone can archive a deal, person or organisation; only an admin can delete one for good (kickoff)
- Any user can import from Pipedrive: they save their Pipedrive API token in their settings, tick what to import (people, organisations, deals, notes, activities, files…) and press Import (kickoff)
- An import never creates a copy of a record it already imported: each imported record keeps its Pipedrive ID (kickoff)
- The import is built and tested with fake Pipedrive data only; the factory never gets a real token (kickoff)
- A saved Pipedrive token is stored encrypted and never shown again (kickoff)
- Each ticked type is imported with all the information the CRM uses for it, not just names; a person's unsubscribed status always comes with them (kickoff)
- A record already imported is left as it is on a new import; the import ends with a report of what was not imported and why (kickoff)
- A Pipedrive record that matches one already in the CRM (a person by email, an organisation by name) is linked to it, never copied (kickoff)
- Pipedrive custom fields with no matching CRM field are not imported: the import report lists them (kickoff)
- Every outside service (Google sign-in, Gmail, Google Calendar, Pipedrive, email sending) is reached through settings and has a fake: the whole app is built and tested without real accounts, and the real ones are set up before go-live (kickoff)
- Open and click tracking is off by default and switched on per email or campaign (kickoff)
- Next.js (App Router) with TypeScript: server components by default, client components only where needed (SF-80)
- No Docker image and no long-running server for the app; it reaches Supabase through Supabase's connection pooler (SF-80)
- Migrations are an explicit command, run in the build of each Vercel production deployment before it goes live, never at app start and never on previews (SF-80)
- Vercel preview deployments only build the app: no database, nobody can sign in (SF-80)
- The CRM has its own Google sign-in and database sessions, not Supabase Auth (SF-80)
- Only barnacle.ai accounts that an admin has added on the Users page can sign in, plus the first admin named in settings (SF-80)
- The fake Google login and the fake data command work only when APP_ENV is exactly "development" or "test"; they are refused everywhere else, including when APP_ENV is not set (SF-80)
- Signed-in pages use design B: a blue left sidebar with the wordmark, the navigation, an "// Admin" group, and the user's name with [ Sign out ] at the bottom (SF-80)
- The Users page uses design A: a table with the actions on each row and the add field above it (SF-80)
- Every table has Row Level Security on with no policies, so Supabase's Data API cannot read or write app data (SF-80)
- Users are deactivated, never deleted (SF-80)
- People and organisation lists and pages use design C: a filter row above the table, a preview drawer when a row is selected, and a one-column record page (SF-90)
- A person added by hand is Subscribed to email until they unsubscribe (SF-90)
- Only admins add, rename and remove lead sources and labels, on an admin page; everyone picks from the lists (SF-90)
- Only admins create, rename, reorder and delete pipelines and stages, on a Pipelines admin page (SF-93)
- The deals board uses design A: rounded cards in stage columns, a pipeline picker and a deal drawer (SF-93)
- Deal cards show no "No next activity" warning until activities exist (SF-93)
- A private deal is visible to its creator and its owner, nobody else, admins included; both can turn Private on or off (SF-93)
- A private person is visible to their creator and their current owner, nobody else, admins included; either of them can make the person private or shared (SF-92)
- When a person is deleted, events about them on other records are kept without their name ("A deleted person …"); events about a person who was private when deleted are removed (SF-92)
- An admin can hand all of a deactivated user's private people to one active user, who becomes their owner; the admin only sees how many there are (SF-92)
- Handing over a deactivated user's private people uses design B: [ HAND OVER ] on the user's row opens a panel above the Users table with the user choice and the question (SF-92)
- Handing over private people removes nothing automatically: the new owner sees the people and their email addresses and can remove an address or make the person shared (SF-92)
- The deal page uses design C: solid Won and Lost buttons in the header, an arrow-shaped stage bar with days per stage, a summary strip, and the lost reason asked in a box over the page; the deal list follows the People list (SF-95)
- A lost reason is typed as free text (SF-95)
- Deal labels are a separate list, managed by admins on the Lead sources and labels page (SF-95)
- A removed deal label stays on the deals that have it and in the list's label filter, and is no longer offered on the edit form, as people labels (SF-95)
- Handing over a deactivated user's private people also hands over the private deals they own, archived ones included, so a private deal is never left visible to nobody (SF-97)
- The timeline uses design B: entries grouped by day with a NOTE, DEAL or CHANGE tag and the time, notes in a box with an orange left edge, the note box above the timeline (SF-102)
- A teammate mentioned in a note is told in the app only: Notifications in the sidebar and a Notifications page, no email (SF-102)
- Anyone who can see a note can edit or delete it (SF-102)
- No browser tests in the repo: Build writes unit and integration tests (on the local Postgres) and never starts the app in a browser; the AI review checks the screens. This replaces the SF-80 choice of Playwright browser tests (2026-11-23)
- The CSV import uses design B: one screen per step (file, columns, preview, report) with a step bar and [ BACK ] (SF-103)
- A CSV row whose email address a person in the CRM already has is not imported; the existing person is left as it is and the report lists the row (SF-103)
- People imported from CSV with no consent in the file get the consent the importing user chooses, with nothing chosen in advance (SF-103)
- The Activities list uses design A: a table like the People list with quick filters Overdue / Today / This week / Planned / Done, the activity form and "Schedule a follow-up?" in a box over the page, and a last line on each board card (SF-109)
- Deal cards show "⚠ No next activity" when the viewer can see no planned activity on the deal, else its next date; this replaces the SF-93 choice (SF-109)
- A done call or meeting sets the linked person's Last contacted to its due date, or the moment it was marked done when the due date is later, never lowering it; a task never does (SF-109)
- A teammate assigned an activity by someone else is told in the app only, on the Notifications page, like a mention (SF-109)
- An ambassador is a person with the Ambassador tick on their form; only ticked people can be chosen as Referred by (SF-114)
- The ambassador page uses design B: its own one-column page with [ PERSON PAGE ], a summary strip, people referred, deals referred, then latest updates grouped by day (SF-114)
- Files use design A: a "// FILES" table between "// NEXT ACTIVITIES" and "// TIMELINE" on record pages and the deal drawer, the image preview in a box over the page, FILE entries on the timeline (SF-116)
- Anyone who can see a record can delete its files, as with notes (SF-116)
- A person's or organisation's "// FILES" lists only their own files; their deals' files show only as FILE entries on the timeline (SF-116)
- A file upload goes straight from the browser to the file store through a write-only link valid for up to 2 hours; the app refuses to finish an upload started more than 2 hours ago, and every link that reads a file lasts 60 seconds (SF-116)
- A PDF preview opens in a new browser tab, in the browser's own PDF viewer (SF-116)
- The Kind column shows JPG, PNG, GIF, WEBP or PDF for files that can be previewed, otherwise the name's ending in capitals when it is 1 to 5 letters or digits, else FILE (SF-116)
- With no file store set up, every file action shows "Files can't be reached right now. Try again in a minute." and nothing is stored anywhere else (SF-116)
- Custom fields use design B: a Custom fields admin page with a tab per kind and a table, the add and edit form and the delete confirmation in a box over the page; values in their own // MORE DETAILS section (SF-115)
- An admin ticks "Show in list" on a custom field; it is the same for every user, at most 8 per list (SF-115)
- A custom field's type cannot be changed: to change it, delete the field and add a new one (SF-115)
- An archived person or deal keeps its custom values on its page, but its edit form hides them and a change to them is refused until it is restored (SF-115)
- Renaming or deleting a custom field or a choice does not change earlier timeline entries: they keep the names of the time (SF-115)
- A custom field's list filter offers the current choices, plus a removed choice only while a record the viewer can see still has it (SF-115)
- A CSV import adds no timeline entry per custom value: an imported record gets only its "imported" entry (SF-115)
- A CSV column heading that matches a custom field name is suggested for the custom field before a built-in field (SF-115)
- The timeline kind check of each migration also lists the kinds of features planned at the same time (SF-115 lists SF-116's file_added and file_deleted), so whichever merges first drops none (SF-115)
- The Pipedrive import uses design B: Settings holds the token; the import has its own page with a step bar (choose, importing, report), like the CSV import (SF-117)
- A Pipedrive contact visible only to its owner is private in the CRM and its owner is its creator: only the owner sees it, not whoever ran the import (SF-117)
- A person Subscribed in the CRM whom Pipedrive says is unsubscribed becomes Unsubscribed on import, with a timeline entry and a report line; an import never makes anyone Subscribed (SF-117)
- Gmail sync copies only email conversations with people in the CRM (2026-11-24)
- Gmail tells the CRM about new mail as it arrives (Gmail push notifications through Google Cloud Pub/Sub); the CRM renews them every day and also checks every 15 minutes for anything missed (2026-11-24)
- Past email comes in only from a "Fetch past emails" button in each user's Gmail settings: it copies the last 12 months of their conversations with people in the CRM, can be pressed again (after an import, for example) and never copies a conversation twice (2026-11-24)
- An email conversation that includes someone a user cannot see (a private person or deal) is hidden from that user entirely (2026-11-24)
- Email templates are shared by the whole team (2026-11-24)
- The Inbox view shows each user only their own mail (2026-11-24)
- Campaigns are sent through the sender's own Gmail (Gmail API), one email per recipient, within Gmail's daily sending limit (about 2,000 per user, everyday email included): at most 1,000 campaign emails per sender per day, so a campaign larger than what is left that day is refused before sending, with the count; no third-party email service. The CRM serves the unsubscribe page and one-click unsubscribe itself, finds bounces in the synced mail and tracks opens and clicks through its own address (2026-11-24)
- Only Google Calendar events with a CRM person as a guest come into the CRM (2026-11-24)
- Saved segments are shared by the whole team. Their recipients are worked out when a campaign is sent, not when the segment is saved: the segment and the send confirmation say so and show the count at that moment (2026-11-24)
- Activity reminders are in the app (the Notifications page and the sidebar count, like assignments) and by email, which Google Calendar sends from the email reminder the CRM puts on the synced event; the CRM sends no reminder email itself. A reminder comes 15 minutes before a timed activity and at 09:00 UK time on the due date of an activity with no time (at once when it is scheduled later that day) (SF-123)
- Any user's Pipedrive import creates the pipelines and stages the CRM lacks (matched by name, never renaming, reordering or deleting one); the only exception to admins-only pipelines (SF-122)
- In the Pipedrive import, ticking Deals, Notes, Activities or Files ticks People and Organisations, which stay ticked (SF-122)
- Pipedrive activities of a type the CRM does not have come in as tasks, counted per Pipedrive type in the report (SF-122)
- Unsubscribe links are a random token per person stored in the CRM, with no expiry; no teammate is told when someone unsubscribes; a teammate's Consent change is shown as 'Consent: <old> → <new>'; the edit form changes Consent only when the field was changed on that form (SF-121)
- Campaigns use design A: the Campaigns page is a table; a draft's edit page has the draft (// DETAILS, // CONTENT) on the left and a live preview for a chosen person on the right (SF-119)
- Campaign drafts are shared by the whole team: everyone can edit, duplicate and delete every draft (SF-119)
- Merge tags of a people custom field follow the field's renames, in the subject, preview text, layout blocks and pasted HTML; a tag typed by hand is matched to its field when the draft is saved (SF-119)
- Segments use design C: a Segments table and one page per segment with a count strip, // WHO and // CONDITIONS; the add and edit form on its own page (SF-120)
- A pipeline or stage segment counts the people on its Open, Won, Lost or All deals, Open first; archived deals never count (SF-120)
- A segment counts each person once, at their first email address, leaving out archived, then unsubscribed, then address-less people (SF-120)
- A segment that refers to a deleted pipeline, stage, organisation or custom field shows it as (deleted), matches nobody through it and asks to be edited (SF-120)
- A segment has at most 20 conditions and a condition at most 100 values; Role and text conditions are at most 200 characters (SF-120, decided by the factory, to confirm)
- The Organisation condition offers every organisation, archived ones included and marked (archived) (SF-120, decided by the factory, to confirm)
- A Single choice condition can pick Empty together with choices; a Yes/No condition picks one of Yes, No or Empty (SF-120, decided by the factory, to confirm)
- Segments make no timeline entries or notifications; only the segment's own Last changed by changes (SF-120, decided by the factory, to confirm)
- Anyone can delete any segment, with no undo, after a confirmation that names it and says it is deleted for the whole team (SF-120, decided by the factory, to confirm)
- Gmail settings use design B: a Gmail card on the Settings page after Pipedrive, and an orange "!" on the one Settings link on every page while Gmail needs reconnecting (SF-118)
- Saved tokens of outside services are sealed by one shared AES-256-GCM module, each service with its own key (PIPEDRIVE_TOKEN_KEY, GMAIL_TOKEN_KEY) (SF-118)
- Emails copied from a user's Gmail are kept when they disconnect or are deactivated (SF-118)
- The 15-minute Gmail check and the daily renewal of Gmail notices run as one Vercel cron job every 15 minutes, on the Vercel Pro plan (SF-118)
- Gmail asks for gmail.modify and gmail.send, so the later Inbox can mark mail read and change labels without every user reconnecting (SF-118)
- After a disconnect, copying starts again from the new connection; after a reconnect from "needs reconnecting", sync carries on from the last successful sync (SF-118)
- Gmail copying uses the time Gmail received or sent a message, not the sender's Date line (SF-118)
- Deactivating a user also cancels their Gmail access at Google (SF-118)
- Google Calendar sync asks for calendar.events.owned and only uses the user's primary calendar (SF-124)
- An activity with no time gets no Google reminder (Google cannot remind at 9:00 on an all-day event); the in-app reminder at 9:00 covers it; activities with a time get Google's email and pop-up 15 minutes before (SF-124)
- Events the CRM puts in Google Calendar are private; tasks with no time are free time (SF-124)
- Deleting in the CRM a meeting that came from Google leaves the Google event; the CRM changes only its title and times, never its guests, description or reminders (SF-124)
- An event deleted in Google, or a meeting from Google that the user declines, ends its sync for good; the activity stays (SF-124)
- Calendar sync runs in the 15-minute Gmail job; changes made in the CRM are sent after the response, never while saving (SF-124)
- After a disconnect, Calendar sync starts again from the new connection: changes made in Google while disconnected are not read; the CRM's values are sent again (SF-124)
- Email on the timeline uses design B: an EMAIL entry with the email in a box with a blue left edge (as notes have an orange one), and the conversation on its own page with // LINKED TO on the left and // EMAILS on the right (SF-127)
- The timeline shows one EMAIL entry per email, each at its own time; opening any of them shows the whole conversation (SF-127)
- A conversation is linked automatically to a private deal like any other; the private deal then hides the conversation from teammates who cannot see the deal (SF-127)
- When the same email is copied into several mailboxes, the sender's copy is shown (so its Bcc shows as the sender sees it); otherwise the copy stored first (SF-127)
- When two copies of a conversation turn out to be one, both sides' links are kept; for the same record a choice made by hand beats an automatic link, and between two choices made by hand the later one wins (SF-127)
- Emails copied before email on the timeline shipped are linked and raise Last contacted the first time the 15-minute Gmail check runs after the release (SF-127)
- A person whose link to a conversation was removed by hand no longer brings a deal to it automatically; their privacy still hides the conversation while they are in its emails (SF-127)
- A conversation can be linked by hand to any deal, person or organisation the user can see that is not archived (Won and Lost deals included) (SF-127)
- An email attachment is always downloaded (never shown in the browser), under its name with the characters a file system refuses replaced (SF-127)
- Copies of one email in several mailboxes are matched by the email's Message-ID (SF-127)
- People and organisations show only the conversations linked to them; a deal's conversations do not also appear on the timelines of the deal's other people or its organisation unless linked to them (SF-127)
- Linking or unlinking a conversation by hand makes no timeline CHANGE entry and no notification (SF-127)
- Automatic links stay when their reason changes (a person changes organisation, a deal closes, an address is removed from a person) (SF-127)
